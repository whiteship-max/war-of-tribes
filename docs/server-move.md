Docker) — решение владельца 04.10.2026. Пошагово для владельца — [SERVER.md](SERVER.md); здесь —

работает как работал: функции стали обёртками общих обработчиков, сборка игры не изменилась ни на

### Договор клиента и сервера

`netlify/lib/contract.ts` — один файл на обе стороны: `SaveRecord`, `PullResponse`, `PushBody`,
`PushResponse`, `ConflictResponse` (сохранение), `CastleClaim`, `RosterResponse` (реестр),
`NotifyPut`, `NotifyState` (уведомления), `cityName` (имя города). Клиент (`src/net/api.ts`)
считает ответом сервера только то, что назвалось JSON: страница игры вместо ответа — «сервера
нет», и игра играет дальше. Серверное «сейчас» (`now`) приезжает с каждым ответом.

**ETag — часть договора, хотя клиент его не разбирает.** Клиент помнит ETag своей последней
записи и по нему решает, его ли это партия на сервере (`src/net/sync.decide`): совпал — своя,
местная копия продолжает её; не совпал — чужая, серверная побеждает, местная уходит в отвергнутые.

### Как используется Netlify Blobs

- `getStore({ name, consistency })` — сайт и токен подставляет платформа;
- чтение текстом с ETag (`getWithMetadata`), условная запись (`setJSON` с `onlyIfMatch` /
  `onlyIfNew`), простая запись (`set`), перечисление с папками (`list({ prefix, directories })` —
  только проход доставки), удаление (`delete` — только доставка);
- строгость: всё строгое, кроме чтения реестра.

### Что по расписанию

Только проход доставки уведомлений — и он заморожен: на Netlify расписаний нет ни одного
(`server.test.ts`, «доставка заморожена»). Время — не расписание, а адрес `/api/time`.
Переменная окружения одна — `TELEGRAM_BOT_TOKEN`.

## 2. Что сделано

**Одна дверь.** Логика каждого адреса перенесена дословно из функции в общий обработчик
`netlify/lib/routes/<имя>.ts` — разница со старым кодом ровно в трёх вещах: хранилище приходит в
`io.stores`, минута — `io.now`, ведро сита частоты ключуется адресом (`save:tg-1`). Функция
Netlify — обёртка в пять строк: путь, Blobs платформы, вызов обработчика. Свой сервер зовёт те же
обработчики из таблицы `routes/index.ts`.

| Файл | Что это |
|---|---|
| `netlify/lib/kv.ts` | дверь хранилища (`Kv`), имена хранилищ (`STORES`) |
| `netlify/lib/blobs.ts` | дом Netlify Blobs |
| `netlify/lib/routes/` | обработчики `save`, `castles`, `notify`, `time` и таблица адресов |
| `netlify/functions/*.mts` | обёртки Netlify (пути — литералом: платформа читает их из исходника) |
| `netlify/vps/sqlite.ts`, `driver.ts` | дом SQLite (встроенный `node:sqlite`) |
| `netlify/vps/listen.ts` | приём HTTP на `node:http` |
| `netlify/vps/config.ts` | настройки из окружения |
| `netlify/vps/backup.ts` | копии: снять, повернуть, восстановить |
| `netlify/vps/schedule.ts` | расписание: копия, отметка «работает», доставка (выключена) |
| `netlify/vps/import.ts` | перенос Netlify Blobs → SQLite |
| `netlify/vps/main.ts` | вход: `serve`, `backup`, `backups`, `restore`, `import-blobs` |
| `netlify/vps/build.mjs` | сборка сервера одним файлом |
| `netlify/vps/log.ts` | журнал своего сервера — только о своих делах |
| `Dockerfile`, `docker-compose.yml`, `.dockerignore`, `.env.example` | образы и запуск |
| `deploy/Caddyfile`, `deploy/update.sh`, `deploy/coolify.yml` | Caddy, обновление, вариант под Coolify |

## 3. Решения

Каждое — с доводом (правило 19); против направления владельца нет ни одного.

1. **Без фреймворка.** Владелец предложил «лёгкий фреймворк»; обработчики уже говорят на
   стандартных `Request`/`Response`, и вся прослойка к `node:http` — один небольшой файл
   `listen.ts` с тестом на настоящем сокете. Фреймворк был бы зависимостью: `package.json` и
   `package-lock.json` менялись бы, а они — в замыкании **всех** отчётов приёмки и в сборке Netlify.
2. **SQLite — встроенный в Node** (`node:sqlite`, без флага с 22.13), а не `better-sqlite3`: без
   нативной сборки и без зависимости. vitest 2 не знает модулей, которые есть только с приставкой
   `node:`, — драйвер берётся через `createRequire` в одном месте (`vps/driver.ts`).
3. **Код сервера — в `netlify/vps/`, а не в `server/` в корне.** Тогда его типы проверяет та же
   ступень `tsc -p netlify` (ступень сборки и `npm run typecheck`), тесты подхватывает
   существующий `test.include`, и ни `vite.config.ts`, ни `package.json` не меняются. Цена —
   папка с именем «netlify» держит код, который не про Netlify; сказано в шапках файлов.
4. **ETag переезжает как есть** (`import.ts`, `sqlite.putRaw`). Новые ETag'и сделали бы каждого
   игрока «чужим» своей же партии (раздел 1, «Договор»).
5. **Сито частоты ключуется адресом.** На Netlify у каждой функции своя память; на своём
   сервере память одна, и общее ведро на игрока резало бы сохранение запросами реестра.
   Заодно поправлена прополка вёдер: полнота считается с доливом по времени и по потолку своего
   ведра (`http.allow`) — прежде по потолку того, кто зашёл последним.
6. **Доставка на сервере выключена по умолчанию** (`TRIBE_DELIVER=off`). Заморозку решал
   владелец; переезд — не повод её снимать. Включить — одной переменной.
7. **Копии — внутри приложения** (`VACUUM INTO` с проверкой целостности, поворот по имени), а не
   cron хоста: один процесс, одна настройка, проверяется тестом.
8. **Восстановление и перенос — только под остановленным сервером** (отметка `serve.alive`,
   свежее 90 с — отказ); нынешняя база перед восстановлением уходит копией `before-restore-…`.
9. **Caddy кэширует куски сборки с хешем год**, остальное — как Netlify (`max-age=0,
   must-revalidate`). Клиенту не видно; повторный заход быстрее.
10. **Упавший обработчик — 500 простым текстом**, как упавшая функция Netlify: клиент читает это
    как «сервера нет» (`api.ts`). Неизвестный путь у приложения — 404 JSON, но до приложения
    неизвестные пути не доходят: Caddy проводит ровно те, что в `ROUTES` (с войной — пять; тест `deploy.test.ts`).
11. **Сервер без токена бота не поднимается.** Netlify с пустым токеном отвечал 401 всем, и игра
    молча шла без синхронизации; лучше не подняться и сказать.
12. **Образы на Node 22** — та же ветка, что у сборки Netlify (`netlify.toml`). `node:sqlite` в 22
    помечен экспериментальным; предупреждение заглушено флагом в `ENTRYPOINT`.
13. **Дом «Netlify Blobs» в тестах — местный сервер Blobs из самого пакета** (им же пользуется
    `netlify dev`) с настоящим клиентом. У него два пробела против настоящего Blobs — нет ETag при
    чтении, ключи в перечислении с процентной кодировкой; оба закрыты в подставном `fetch`
    (`vps/testkit.ts`), иначе тест отличался бы от боевого ровно тем, что проверяет.

### Мутации (правило 11)

Каждая — порча одного места, прогон, возврат байт в байт. Скрипт и спека — в рабочей папке сессии,
не в репозитории; записано, что упало.

| Мутация | Упало (тест › утверждение) |
|---|---|
| SQLite: `onlyIfMatch` без условия на ETag | kv › «поверх ровно этой версии» (`true` вместо `false`); routes › гонка «поверх своей версии» (200 вместо 409) |
| SQLite: `onlyIfNew` пишет поверх | kv › «только в пустое место»; routes › гонка «в пустое место» (200 вместо 409) |
| Blobs: условие записи теряется | kv › три утверждения условной записи на Blobs |
| SQLite: папки не сворачиваются | kv › перечисление (`[ '000100/tg-1', … ]` вместо `[ 'loose' ]`) |
| перенос: ETag не сохраняется | import › «ETag в ETag»; import › «игрок переезда не замечает» (409 вместо 200) |
| сито: общее ведро у реестра и сохранения | routes › «у адресов свои вёдра» (429 вместо 200), оба дома |
| приём: тело режется ровно по потолку | listen › «потоком, без заявленной длины — тоже 413» (400 вместо 413) |
| приём: адрес — левый в `X-Forwarded-For` | listen › «адрес клиента — правый» |
| расписание: доставка без слова владельца | schedule › «без слова владельца не идёт» |
| восстановление под живым сервером | backup › «под живым сервером не идёт» |
| Caddy потерял `/api/notify` | deploy › «список @api совпадает с ROUTES» |
| compose: порт приложения наружу | deploy › «у приложения нет портов наружу» |
| функция Netlify ведёт не в свой обработчик | functions › «castles.mts зовёт обработчик своего пути» |
| сохранение: хранилище открыто до подписи | server › «подпись проверяется до первого похода в хранилище» |
| `.dockerignore` пропускает `.env` | deploy › «.env не попадает в контекст сборки» |

В первом прогоне не поймались три мутации. Две — по делу, и они дали два теста: «`onlyIfNew` пишет
поверх» обработчик отсекает ещё до записи (сверка ETag) — условная запись спасает только в гонке,
и гонки в тесте договора не было; «тело режется по потолку» маскировала проверка заявленной длины —
не было случая тела потоком. Третья была испорчена сама (потерянная кавычка — «no tests»).

## 5. Чего нет и что не проверено

- **Docker на машине разработки не установлен**: образы не собирались, `docker compose` не
  запускался, `Caddyfile` не проверен самим Caddy. Проверено то, что можно без Docker: сервер

  этап 2, на сервере.
- **Coolify не проверен на живой панели** — `deploy/coolify.yml` и шаги в SERVER.md написаны по
  его устройству (прокси на 80/443, домен на сервис).
- **Перенос на настоящем Netlify Blobs не гонялся** — нужен личный токен владельца; проверен на
  местном сервере Blobs.
- **Комментарии в `src/world/` (`tuning.ts`, `gen.ts`, `land.ts`, `local/state.ts`, `settle.ts`)
  называют `netlify/functions/castles.mts`** — путь жив (обёртка ведёт в
  `lib/routes/castles.ts`), правка комментариев ядра — отдельной мелкой задачей, не по дороге.
- **`SITE_URL` в `src/game/data/social.ts`** — боевой адрес Netlify, им игрок делится ссылкой.
  Ядро (словарь); менять тем же коммитом, что и переключение бота, когда домен известен (этап 2).
- **Обратного переноса** (SQLite → Netlify Blobs) нет: откат на Netlify возвращает игроков к
  данным на Netlify на минуту переезда (SERVER.md, «Откат»). Живых игроков нет — не делалось.
