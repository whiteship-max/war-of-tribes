# war-of-tribes: план работ по исправлению багов

**Для кого:** для ИИ-ассистента или разработчика, который будет вносить исправления.
**Основание:** два раунда аудита коммита `d1784a7`.
- Проверено около 82 000 строк: сервер (`netlify/`), бой (`src/battle`), сеть (`src/net`), ядро (`src/game`), мир (`src/world`, включая `LocalWorld.ts`).
- Подтверждено **44 бага**: 26 в первом раунде, 18 во втором. Каждый баг второй агент независимо подтвердил падающим тестом или чтением кода.

**Сопровождающие файлы:**
- `regression-tests.tgz` — тесты, воспроизводящие баги: `round1/…` — первый раунд, `round2/prove-N-1/…` — второй.
- `OWNER-DECISIONS.md` — вопросы, где нужно решение владельца. Если ответа нет, бери вариант «рекомендую».

## 0. Правила работы (прочитать до начала)

1. **Не трогать механику голода, истощения и изнурения при осаде** (siege hunger/starvation/attrition, `garrisonWear`, `wearSpan`, larder). Её сейчас переписывают. Если исправление задевает этот код, остановись и отметь задачу как «ждёт осаду».
2. **Одна задача — один коммит**, в сообщении указывается ID задачи (`FIN-1`, `ECO-2`…).
3. **Сначала тест, потом исправление.** К каждой задаче добавь регрессионный тест рядом с кодом (`*.test.ts`, vitest). До исправления он должен падать, после — проходить. Можно взять тест из архива и переписать под vitest. Пути вида `prove-N-1/...` и `round1/...` указаны внутри архива.
4. **Пары клиент–сервер.** Если формула есть и в `src/`, и в `netlify/`, меняй обе стороны в одном коммите. Если можно, вынеси формулу в общий модуль в `src/game/`, который импортирует сервер (так уже сделано с `build.ts` и `labour.ts`).
5. **Детерминизм боя.** Задачи с пометкой ⚔️ меняют результат боя. Их собирают в один релиз с номером версии правил боя (см. `BTL-0`).
6. **Сохранения.** Новое поле в `GameState` или в карточке сохранения требует:
   - значения по умолчанию для старых сохранений;
   - прохождения через валидатор и сериализатор (`save.ts`, `contract.ts`);
   - теста загрузки старого сохранения.
7. **После каждого этапа:** `npm run typecheck` и `npm test` должны быть зелёными.
8. Если описанное поведение похоже на задуманное, не исправляй молча: отметь вопрос в `OWNER-DECISIONS.md`.

## Этап 1. Деньги: TON, Stars, алмазы (критично)

### FIN-1 [High] Сканирование TON обрезается на 500 транзакциях
- **Файлы:** `netlify/lib/ton.ts` (`incoming`, около строки 262), `netlify/lib/pay.ts` (`huntTransfers`, около строки 229).
- **Суть:** просмотр начинается от самого старого «охотящегося» заказа (неоплаченный висит 7 дней) и обрывается после 5×100 транзакций без сигнала. Новые платежи не видны. Любой игрок может «прибить» окно, оставив заказ неоплаченным.
- **Решение:**
  1. В хранилище `pay` завести запись `cursor:<wallet>` = `{ lt, hash, utime }` последней **финальной** просмотренной транзакции.
  2. `incoming(wallet, cursor)` читает страницы от курсора вперёд (`sort=asc`), пока не придёт неполная страница или не кончится бюджет запросов. Бюджет — например 20 страниц за вызов. Функция возвращает `{ txs, next, truncated }`.
  3. Курсор сдвигается только до последней транзакции с `final === true` (см. `FIN-2`). Нефинальные пересматриваются в следующий раз.
  4. Если `truncated`, проверку повторить при следующем вызове. Платёж не теряется, только задерживается.
  5. Каждую транзакцию сопоставлять со всеми открытыми и «охотящимися» заказами по комментарию и сумме, как сейчас.
- **Приёмка:** тесты `round2/prove-5-1/repo/t5.test.ts` и `prove-12-1/repo/t12.test.ts` проходят: из 650–1000 транзакций виден последний платёж. Добавить тест «курсор не прыгает через нефинальную транзакцию».
- **Риски:** лимит toncenter (около 1 запроса в секунду без ключа, таймаут 8 с) — нужен бюджет и повтор при следующем вызове. Двойного начисления не будет: `claimTx` записывает только новое (`onlyIfNew`).

### FIN-5 [Medium] Ускорение оплачено, но стройка закончилась сама — алмазы потеряны
- **Файлы:** `src/game/sim/gems.ts:134` (`applyGemDeeds`), `netlify/lib/gems.ts`, `routes/save.ts`, `contract.ts`.

### FIN-6 [Medium] Смена эпохи и платежи
- **Файл:** `netlify/lib/era.ts`.
- **Суть:** `WIPED` не включает хранилище `pay`, а список защиты от двойных покупок `paid[]` хранится в стираемом хранилище алмазов. После `/wipeworld` заказ в состоянии «оплачен, не зачислен» может зачислиться второй раз или потеряться.

- **Приёмка:** тест «wipe между оплатой и зачислением → ровно одно начисление».

## Этап 2. Ресурсы и экономика ядра

### ECO-1 [High] Склад выше лимита срезается до лимита (7 мест) — нужна общая функция
- **Файлы:** `src/game/sim/tick.ts:91`, `src/game/sim/pay.ts:49` (`refund`, через неё `cancelUpgrade`), `src/game/sim/caravan.ts:97`, `src/game/sim/gate.ts:50`, `src/game/sim/expedition.ts:345`, `src/game/data/eventKit.ts:32`. На сервере: `netlify/lib/goods.ts:104` и `:134`.
- **Суть:** `res = Math.min(cap, before + n)` уменьшает запас, который уже выше лимита. Купленное за алмазы через `layStock` намеренно лежит выше лимита и **сгорает на следующем тике производства**.
- **Решение** (вариант A из `OWNER-DECISIONS` — запас выше лимита разрешён):
  ```ts
  // src/game/sim/stock.ts
  export function addStock(s: GameState, r: ResourceId, n: number, cap = storageCap(s)): number {
    const before = s.resources[r] ?? 0;
    s.resources[r] = n > 0 ? Math.max(before, Math.min(cap, before + n)) : Math.max(0, before + n);
    return s.resources[r] - before;
  }
  ```
  - `layStock` становится обёрткой над `addStock`. Все 7 мест переводятся на `addStock`.
  - ⚠️ **В `tick.ts` производство бывает отрицательным** (отопление вычитается из `prod.wood`, `derived.ts:1302`). Формула со знаком выше это учитывает. Формулу `Math.max(before, …)` без знака в тик **не вставлять**: дерево станет бесконечным.
  - Сервер `goods.ts`: остаток после выработки = `n>0 ? max(prev, min(cap, prev+n)) : max(0, prev+n)`, то есть то же правило через общую функцию.
- **Приёмка:** тесты `round1/game-core/prove-3-1, -7-1, -14-1, -15-1, -16-1, -17-1, -18-1`. Новые тесты:
  - отрицательное производство уменьшает запас выше лимита;
  - клиент и сервер дают одинаковый остаток на 100 случайных сценариях.
- **Риски:** если менять только клиент, сервер будет считать склад меньшим и давать ложные флаги. Менять обязательно вместе.

### ECO-2 [High] Долг купцу пересчитывается по текущему населению (эксплойт)

### ECO-3 [High] Последствия событий фиксировать при создании события (системная задача)
- **Файлы:** `src/game/data/events.ts`, `tidings.ts`, `src/game/sim/mail.ts`.
- **Суть:** условия события проверяются при его появлении, а стоимость и награда пересчитываются при ответе. Ответить можно до суток спустя. Отсюда:
  - второй обряд за сезон через «праздник» (подтверждено тестом);
  - повторная реликвия;
  - найм без стройки;
  - сдвиг цены и награды при изменении населения;
  - пожар во время стройки.
- **Решение:**
  1. У `EventOption` поле `block?: (s) => string | null`. `eventBlock` вызывает его после проверки ресурсов.
  2. Для каждого события, у которого в `weight` есть условие состояния, продублировать это условие в `block`:
     - праздник: `riteInfo(s).blocked`;
     - `relic_offer`: «реликвия уже есть»;
     - «нанять на день»: `currentSite(s)`;
     - шторм: та же стройка.
  3. В `ActiveEvent` при создании сохранять `frozen: { cost, reward }`, вычисленные функциями опции. `payEventCost` и `apply` берут их оттуда, а для старых событий без `frozen` считают как раньше.
  4. Перебежчики: число людей сохранять в звене цепочки при планировании.
- **Приёмка:** `round1/game-core/prove-4-1/.../rite2.test.ts`. Тест на каждое событие с `block`. Тест «цена в ответе равна цене при создании».

## Этап 3. Античит (сервер)

### AC-1 [High] Счётчик `deeds` от клиента выключает проверки роста и укрытия склада
- **Файлы:** `netlify/lib/watch.ts:498` (`flagsBetween`), `netlify/lib/goods.ts:89` (`quietBetween`, `goodsStep`).
- **Суть:** проверки роста склада, армии, долгов и возвратов, а также нижняя граница склада против грабежа работают только между «тихими» карточками. Тихость решают счётчики, которые присылает клиент. Прибавка `deeds += 1` на каждом сохранении:
  - даёт любые ресурсы без флага;
  - прячет склад от налётчика.
- **Решение (проектное, в три шага):**
  1. **Таблица максимальных наград.** Сгенерировать из игровых данных `MAX_DEED_GAIN[resource]` и `MAX_DEED_TROOPS`: максимум, который может дать одно дело (событие, логово, набег, караван, лавка). Генерировать скриптом, в CI проверять, что таблица совпадает с данными.
  2. **Допуск вместо выключения.** Проверки идут всегда:
     - `could = производство × dt + Δdeeds × MAX_DEED_GAIN + подтверждённое сервером (указы, алмазы, война, рынок)`;
     - для укрытия склада: `floor = прежний − расход × dt − Δoutlays × MAX_OUTLAY`.
  3. **Флаг подделки счётчика.** Рост `deeds` выше `DEEDS_PER_MIN_MAX × минуты` или без событий, которые видит сервер, — флаг `deeds`.
  - В долгосрочной перспективе: сервер сам считает дела по своим журналам.
- **Приёмка:** `round2/prove-7-1/.../p7.test.ts` и `prove-13-1/.../c13.test.ts` ловят подделку. Тест «честная партия: шесть часов сохранений раз в минуту без ложных флагов» (такой уже есть в проекте, `cityrules`) проходит.
- **Риск:** заниженный допуск даёт ложные флаги честным игрокам. Константы только из данных. Версия с угаданными лимитами уже провалилась.

### AC-2 [High] Указ админа съедается раньше, чем клиент его применил
- **Файлы:** `netlify/lib/watch.ts:1080` (`booked`), `netlify/lib/book.ts:264`.
- **Решение:** передавать в книгу только применённые указы: `grants.filter((g) => g.n <= (watch.seen ?? 0))`. Поле `seen` уже есть в карточке (`contract.ts:1826`, `src/net/snapshot.ts:106`).

## Этап 4. Бой и война ⚔️

### BTL-0 Версия правил боя
- Ввести `BATTLE_RULES = N` в `src/battle/config.ts`. Писать её в отчёт о бою и в серверную запись войны.
- Пересчёт и повтор старого боя идёт по его версии, либо старые бои не пересчитываются.
- Все задачи ⚔️ ниже выкатывать одним релизом с `N + 1`.

### BTL-1 [High] ⚔️ Тяжёлые войска не несут потерь (`spreadLosses`)
- **Файл:** `src/game/battle/price.ts`. Используется в `world/fights.ts`, `LocalWorld.ts` и `netlify/lib/war.ts`.
- **Решение:** floor по каждому виду, затем остаток отдать одним бойцом первому виду, у которого остались люди:
  ```ts
  for (const id of TROOPS_OF_KIND[kind]) {
    const have = Math.max(0, t[id] ?? 0), w = battleWeight(id);
    if (have <= 0 || left <= 0) continue;
    const take = Math.min(have, Math.floor(left / w));
    if (take > 0) { out[id] = take; left -= take * w; }
  }
  if (left > 1e-9) for (const id of TROOPS_OF_KIND[kind]) {
    if (Math.max(0, t[id] ?? 0) - (out[id] ?? 0) > 0) { out[id] = (out[id] ?? 0) + 1; break; }
  }
  ```
- `menOf` / `kindsOf` (`max(1, round(n*w))`) выровнять тем же принципом.
- **Не использовать** `Math.ceil`: слабые войска будут гибнуть сверх своей доли.
- **Приёмка:** `round1/game-core/prove-2-1/t.ts`. Тест «сумма снятых весов отличается от потерь меньше чем на один вес».

### BTL-2 [High] Один полководец в двух битвах (выручка, поход, удар)
- **Файл:** `netlify/lib/war.ts` (`applyOrder`: `relief`, `march`, `strike`).
- **Решение:** одна функция `generalBusy(file, key)` — есть атакующая война, выручка в пути или удар по лагерю у своих стен. Вызывать её во всех трёх приказах. Клиентский `WAR_BUSY` привести к тем же правилам.
- **Приёмка:** `round2/prove-17-1/.../relief17.test.ts`, `prove-18-1/dbl.test.ts`.

### BTL-3 [High] Вера превращает армию в ополчение
- **Файлы:** `src/game/build.ts:86`, `src/world/bridge.ts:70`.
- **Решение:** `militiaOf(defense, homePower, steadfast = 0) = max(0, round((defense − homePower·(1+steadfast)) / BATTLE_MAN))`. Вызов в `bridge.ts` передаёт `faithTilt(s).steadfast`.
- **Приёмка:** `round1/game-core/prove-12-1/t.ts`.
- **Баланс:** у игроков с верой станет меньше ополчения и лучников на башне. Это ожидаемо.

### BTL-4 [Medium] Залп записывается в устаревший объект лагеря

- **Решение:** после `ringCheck(w, at, sheet)` перечитать `camp = w.camp as SiegeWindow`. Проверить ветку штурма. Клиентский siegeroll должен давать тот же результат.

### BTL-5 [Medium] ⚔️ Одинокий всадник уходит в резерв
- **Файл:** `src/battle/setup.ts` (`fill`, ветка `'edges'`).
- **Решение:** `if (left > 0) center();`
- **Приёмка:** `round1/server-battle-net/prove-6-1/t.ts`.

### BTL-6 [Medium] Потери рыцарей списываются с дубинщиков

### BTL-7 [Medium] Размер отряда расходится с тем, кто ушёл из дома
