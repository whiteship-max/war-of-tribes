# TRIBE — Telegram Mini App

Лёгкая low-poly 3D-стратегия о племени позднего средневековья: посёлок стоит с первой секунды,
а игра — про дружину, карту и бой. Полное видение — в [docs/concept.md](docs/concept.md).
Заход 3–5 минут: поставить людей, сковать снаряжение, нанять отряд, отправить разведку или
поход, принять решение в событии, улучшить здание.

## Стек

- Vite + TypeScript + React 18 (2D-интерфейс поверх сцены)
- three.js (low-poly диорама, OrbitControls с ограничениями под тач)
- zustand (единый стор), vitest (тесты симуляции)
- Telegram WebApp API через `window.Telegram.WebApp` (скрипт в index.html); сохранение в localStorage + CloudStorage

## Команды

```bash
npm run dev        # dev-сервер (vite --host)
npm run build      # tsc + vite build → dist/
npm run preview    # раздать собранное (порт 4173) — так проверяют продакшен-сборку
npm test           # vitest
npm run typecheck
```

## Выкладка

Постоянный адрес — **https://gleeful-sunflower-a2f83c.netlify.app**. Он же стоит Menu Button'ом
в @BotFather, поэтому меняться не должен: каждый деплой обновляет его на месте. Адреса вида
`<хеш>--gleeful-sunflower-a2f83c.netlify.app` — снимки отдельных сборок, для ссылок они не годятся.
Исходники — https://github.com/whiteship-max/war-of-tribes (приватный), Netlify собирает `master`.
Туннели больше не нужны.

Игра — статика: `vite build` кладёт всё в `dist/`, `base: '/'` (абсолютные пути к чанкам, иначе
на подпути ломается). Сервера нет, состояние живёт в localStorage и Telegram CloudStorage,
переменных окружения у сборки нет — токен бота живёт только в @BotFather.

- Приложение одностраничное: любой путь должен отдавать `index.html`. Это записано сразу для двух
  хостингов, чтобы не переписывать при переезде: `netlify.toml` (+ `public/_redirects`) и
  `vercel.json`. Node — 22 (`.nvmrc`, `NODE_VERSION` в `netlify.toml`).
- Команда сборки на хостинге — `npm run build`, папка вывода — `dist`.
- **Сайт обязан быть публичным.** Netlify новым сайтам включает Team protection, и тогда любой
  заход редиректит на форму входа Netlify — в браузере разработчика этого не видно, он залогинен,
  а с телефона и из Telegram игра просто не откроется. Настройка: Site configuration →
  Access & security → Visitor access. Проверять — приватным окном, не своим браузером.
- Размер сборки: ~930 КБ на диске, по сети ~265 КБ gzip (three 125, игра 82, react 45, стиль 5).
  Стенд — отдельный чанк ~4 КБ gzip, грузится только по `?showcase=`.
- Проверять правки перед выкладкой надо именно на `npm run preview`, а не на dev-сервере:
  у dev-сервера есть `/__snap` и `/__perf`, которых на хостинге нет.

### Стенд в проде

Стенд открывается по тому же адресу — он собирается в продакшен нарочно (см. «Графика»).
Замер частоты кадров на телефоне теперь делается без туннеля:

```
https://gleeful-sunflower-a2f83c.netlify.app/?showcase=village&levels=10&perf=8
```

Экран не гасить и вкладку не сворачивать: в фоне `requestAnimationFrame` стоит, и замер выйдет
нулевым. Прогрев полторы секунды, потом камера крутится восемь секунд. Итог остаётся в подписи,
а тап по ней кладёт отчёт целиком (устройство, dpr, вызовы, треугольники) в буфер обмена —
класть его в `snaps/perf.jsonl` некому, `/__perf` есть только у dev-сервера. Снимки (`?snap=имя`)
в проде тоже не сохраняются: за ними — на `npm run dev`.

## Старт в позднем средневековье

Эволюционного развития в игре нет — ни эпох, ни технологий, ни стадий поселения. Всё, что
раньше открывалось знаниями, считается изученным и сложено в базовые числа: выработка профессий
(`data/jobs.ts`), жильё хижины, скорость стройки (`BUILDER_RATE`), оборона без бойцов
(`BASE_DEFENSE`), мораль устоявшегося племени (`MORALE_BASE`). Нового «уровня развития» заводить
нельзя: следующая сессия, работая по старому описанию, вернёт лестницу открытий — этого и не надо.

- **Новая партия начинается с готовым посёлком**: все здания первого уровня, включая стену,
  башню, казармы, кузницу и рынок (`createInitialState` идёт по `BUILDINGS` целиком). Стройки
  с нуля нет: у здания нет уровня 0, площадок и этапов модели.
- **Уровни и улучшение — единственная прогрессия посёлка.** Потолок — `def.maxLevel` и общий
  `MAX_BUILDING_LEVEL` (10), ничем сверху не режется.
- **Все гейты сняты.** Золото, налог, рынок, казармы, все семь видов бойцов и всё снаряжение
  кузницы доступны с первой секунды; замки на карте видны с начала. У зданий, профессий,
  снаряжения, войск и товаров нет поля `requiresTech`, и его нельзя заводить обратно.
- **Лестница войск — не порядок открытия.** Список в казармах идёт от дешёвого к дорогому, выбор
  между видами тактический (кто против кого, см. «Бой») и экономический (снаряжение, люди,
  припас). Порядок в `TROOPS` — порядок показа, не доступности.
- **Старые сохранения не приводятся.** `SAVE_VERSION` — 5, миграций нет: сохранение младшей
  версии `deserialize` отбрасывает, `loadGame` возвращает `legacy: true`, и `LegacyModal` говорит
  игроку прямо, что партия начата заново. Молча стирать нельзя. Сохранение мира — версия 2,
  вместе с новой партией приходит новый мир.

## Диегетический интерфейс

Данные живут не в глобальных панелях, а внутри зданий. Одно правило без исключений:

- у каждого здания своя панель, она открывается тапом по зданию в сцене или из списка в «Зданиях»;
- панель у всех одинаковая: шапка (иконка, название, уровень, кнопка улучшения), слоты рабочих,
  собственные данные здания, его действия — см. `ui/panels/BuildingPanel.tsx`;
- ресурсы и снаряжение целиком видны только на складе, вольный сбор и мораль — у костра,
  указы, рацион, налог и казна — в Доме вождя, ковка — в кузнице, наём — в казармах,
  закупка за золото — на рынке;
- нижняя навигация — только то, что не привязано к месту: «Племя», «Здания», «Задания».
  «Здания» (`ui/panels/BuildPanel.tsx`) — список посёлка: сначала «В работе» (улучшения),
  потом «Посёлок» (тап открывает панель здания, у карточки есть `data-tut="list-<тип>"`).
  Раздела «можно построить» нет — строить нечего, всё стоит. Тап по крыше в сцене остаётся,
  но основной путь к зданию — список: на 390 px пальцем по крыше не попасть.
- в строке состояния (`TopBar`) — день, сезон, население, мораль и дружина; справа кнопка карты,
  видна всегда.

Игрока нельзя запереть за зданием: добыча без места в здании работает «вольным сбором»
(`FREE_RANGE_MULT`).

## Дом вождя: указы, рацион, налог

`data/policy.ts` — единственное место, где записано, что делают указ, рацион и налог. Логика
только читает таблицу: `decreeOf`/`rationOf`/`taxOf`, множитель выработки в `jobMultiplier`,
множитель расхода в `foodConsumptionPerDay`, дневной сдвиг морали в `tick` через
`policyMoralePerDay`.

- Налог даёт `perPop × население × TAX_PER_POP` золота в день, население — жители, бойцы и
  новобранцы (`population`). Платит за него мораль.
- Последствия пишутся словами в поле `effect` — этот текст стоит **на кнопке**, а не в подсказке.
- Числа должны сходиться ровно: тест сверяет выработку и расход с объявленной величиной.
- Дом вождя с 6 уровня даёт жильё — через поле `since` в определении здания.

## Снаряжение и войско

- **Снаряжение** (`data/equipment.ts`) — счётчики в `s.equipment`, а не ресурсы. Вместимость склада
  на них не действует (полный склад молча остановил бы кузницу) и чужой набег их не уносит.
  Видны они всё равно на складе, отдельным разделом. Куётся всё с первого дня.
- **Кузница** кует выбранное (`s.forging`), скорость — из числа кузнецов, уровня здания и таланта
  (`forgeRate` через `villagerMultiplier`). Не хватает материалов — заготовка ждёт, а панель пишет,
  чего именно. Молчаливого тупика быть не должно. У строк наряда есть `data-tut="forge-<предмет>"`.
- **Войско** (`data/troops.ts`) — счётчики в `s.army`. Боец не житель с профессией: роли «воин» в
  `JobId` нет. Цена найма — ресурсы + снаряжение + один свободный житель + время учений; всё
  списывается сразу, как за стройку. Ушедшие на учения хранятся в самом заказе (`RecruitOrder.people`),
  поэтому отмена возвращает тех же людей, а не безымянные головы. У кнопки найма —
  `data-tut="recruit-<вид>"`.
- Очередь найма одна и идёт последовательно; остаток работы переходит следующему заказу.
- **Мощь армии считается из состава отряда** (`armyPower`) и ничем больше не множится: снаряжение уже
  вложено в вид бойца. Эту же мощь берёт карта мира через `soldierPower` в `world/bridge.ts`.
- Бойцы едят (`SOLDIER_FOOD`), но жилья не требуют: они живут в казармах. Дружина — главный
  сток еды, и это она делает зиму задачей.
- **Мастерская** — про стройку: ремесленники ускоряют улучшения (`crafterBuildRate`,
  `CRAFTER_BUILD`), других дел у неё нет.

## Золото и рынок

Золото есть с первого дня: стартовая казна, налог в Доме вождя и рынок у ворот.

- **Золото — не ресурс.** Оно лежит в `s.gold`, вместимость склада на него не действует, и чужой
  набег его не уносит: казну прячут, а не сваливают в амбар. Видно его там, где им пользуются, —
  в Доме вождя (казна и налог) и на рынке.
- **Налог** — просадка морали вычитается **после** приведения цели к шкале (`moraleTarget`): иначе
  в большом посёлке, где мораль и так упёрлась в потолок, налог не стоил бы ничего. Низкая мораль
  режет всю выработку, поэтому высокий налог выгоден в короткую, но не как уклад — тест сверяет,
  что за игровой год он приносит меньше, чем отнимает.
- **Рынок** (`data/market.ts`, `sim/market.ts`) — здание у ворот, одно, растёт уровнями.
  За золото покупаются ресурсы и снаряжение из ассортимента кузницы.
  Правило баланса одно: **покупать всегда заметно дороже, чем производить самому**. Держится оно
  на трёх ограничителях, и каждый проверяется тестом:
  1. цена не опускается ниже `selfCost × MIN_MARKUP` ни при каком уровне рынка — уровень добавляет
     запас и ассортимент, но не скидку;
  2. дневной запас (`goodStock`) ограничивает, сколько уйдёт с прилавка за игровой день;
  3. цена каждой следующей единицы за день выше предыдущей (`PRICE_RAMP`), и считается она
     поштучно — дробление покупки не даёт ни лимита в обход, ни копейки скидки.
  Еда — самый дорогой товар и с самым жёстким запасом: дневного запаса не хватает, чтобы
  прокормить посёлок с дружиной, поэтому зима остаётся угрозой, а не строкой расходов.
- **Ассортимент нигде не хранится**: он выводится из номера игрового дня (`offerFor`), поэтому
  перезагрузка не тасует прилавок, а сервер потом получит тот же список из того же числа.
  В состоянии живёт только счётчик купленного за день (`s.market`).
- **Караван** (`s.caravans`). Золото списывается сразу, груза на складе нет, пока телега не
  вернётся из ворот: в сцене она едет по главной улице (`render/caravan.ts`). Отмена возвращает
  золото целиком и освобождает дневной запас.
- **Второй источник золота — замки на карте мира.** См. раздел про карту.
- Интерфейс рынка — две вкладки: закупка у проезжих торговцев и место под торг между игроками.
  Торга между игроками нет и не должно появиться до сервера.

## Проводка первых шагов

Новичок видит готовый посёлок, и ему негде прочитать правила: полосы ресурсов нет, данные спрятаны
в здания. Поэтому первая партия ведётся за руку — `game/data/tutorial.ts` (шаги) и `ui/TutorialOverlay.tsx`
(строка и «дырка» в затемнении). Путь — вокруг того, про что игра: тапнуть кузницу → поставить
кузнеца → выбрать наряд на копьё → открыть «Здания» → найти казармы → нанять копейщика (строка
объясняет ожидание, пока копьё куётся) → открыть карту → тапнуть соседа → отправить разведку.

- Ни одного шага без действия игрока: экранов с «Далее» нет, шаг закрывается настоящим тапом
  в настоящем интерфейсе. Исключение — строки-заставки в начале и в конце, они закрываются тапом
  в любом месте.
- Шаг засчитывается по факту (`done(s, ui)`), а не по порядку: нанял бойца до просьбы — шаги про
  наём проматываются. Условие пишется щедро, чтобы игрок не застрял на уже сделанном.
- Обучение видит интерфейс (`TutorialUi`): открытую панель здания, раздел навигации, открытую
  карту и карточку клетки. Слой рисуется и поверх карты; разведка засчитывается по
  `s.scoutsAway`, который мир проставляет на пульсе.
- Симуляция не останавливается. Слой ничего не перехватывает: затемнение — это тень самой «дырки»
  (`box-shadow` наружу), у неё `pointer-events: none`.
- Подсветка здания считается проекцией из 3D (`TribeScene.screenSpot`) каждый кадр — она не отстаёт
  при повороте камеры. Подсветка интерфейса ищется по `data-tut`.
- Прогресс живёт в сохранении (`tutorialStep`, `tutorialDone`), а не в отдельном ключе localStorage.
- Пока обучение идёт, `tick` придерживает случайные события — но не дольше `TUTORIAL_EVENT_MUTE`,
  иначе брошенное на середине обучение выключило бы их навсегда.
- Отладка: «Задания» → «Служебное» → «Пройти обучение заново».

## Визуальный рост зданий

Уровень виден в сцене, иначе он остаётся числом в панели.

- Три ступени на здание: уровни 1–3, 4–7, 8–10 (`VISUAL_TIERS`, `visualTier`). Каждая следующая заметно
  крупнее и подробнее: у хижины появляется пристройка, потом крыльцо и труба; у рудника — копёр, потом
  колесо и рельсы; у Дома вождя — палата, потом донжон с зубцами; у стены — камень, башни, стяг.
- Внутри ступени постройка ещё подрастает масштабом (`levelScale`), а весь посёлок ужат общим
  множителем плана `PLAN_SCALE`: модели рисовались под прежнюю вольную расстановку и для кольцевого
  посёлка велики. Стена — исключение: она и есть это кольцо, её масштабировать нельзя.
- Стиль один на всю игру — позднее средневековье: `ROLES` (какие цвета палитры у ролей: штукатурка,
  черепица, каменный цоколь) и `FEATURES` (черепичная кровля, каменная труба, окна, фахверк,
  пологая крыша) в `render/buildings.ts`. Материалы старых моделей — `STYLE`, краски набора
  деталей — `stylePaint()`. Новый материал крыши надо добавить и в `render/season.ts`, иначе
  зимой он не побелеет. То же для новых материалов дорог и разметки.
- Модель пересобирается только при смене ступени — не на каждом уровне.
- Улучшение модель не трогает: вокруг неё появляются леса (`scaffold`), здание работает, рабочие
  ходят туда же. Этапов стройки (площадка, каркас) нет — строить с нуля нечего.

## Графика: палитра, свет, набор деталей

Стиль — low-poly с плоским затенением, без текстур. Качество делают свет, цвет и посадка в землю,
а не полигоны. Четыре модуля держат это, и правила у них жёсткие:

- **Палитра** (`render/palette.ts`) — единственное место с hex. Все материалы (`render/materials.ts`)
  и сезонные переопределения берутся из неё по имени; цвет «по месту» — ошибка. Чистого белого и
  чёрного нет ни в одном канале, кроме огня и источников света (`palette.test.ts`). Сезон не заменяет
  палитру, а переопределяет её часть (`SEASON_OVERRIDES`): снег ложится на то, что лежит горизонтально —
  землю, кроны, кровли, дороги, — а стены, столбы, цоколь и металл остаются собой. Новый материал,
  на который ложится снег, обязан попасть в переопределения зимы.
- **Материалы** — три набора: `KIT` с цветом вершин для склеенной геометрии, `LEGACY` без него для
  старых моделей, `DECAL` для наложений на землю. Материал с `vertexColors`, получив геометрию без
  атрибута `color`, красит её чёрным — наборы не смешивать; `kit.test.ts` проверяет инвариант
  на всех моделях всех ступеней.
- **Свет** (`render/lighting.ts`) — один тёплый направленный источник с тенью, слева-спереди от
  стартовой камеры и никогда в зените (52° в полдень), холодная полусфера сверху и тёплая снизу,
  `NeutralToneMapping`. Синева теней получается сама: в тени поверхность видит только полусферу.
  Второй источник с тенью не заводить. Ночью та же лампа становится луной. Риг общий для игры и
  стенда — иначе снимки со стенда ничего не доказывают. Всё, что не должно тонмапиться (маркеры,
  кольцо выбора, огонь, снег), помечается `toneMapped: false`.
- **Набор деталей** (`render/kit.ts`) — здание собирается из общих деталей (стена, цоколь, конус и
  двускатная кровля, столб, крыльцо, труба, дверь, окно, фахверк, ограда) и склеивается в
  один меш: группы по материалу, один вызов отрисовки на материал. Несезонные детали пекут цвет
  палитры в вершины на общем «теле» (`KIT.body`), сезонные (кровля, пашня) — настоящие материалы,
  чтобы их переливал сезон. В вершины запекается и контактное затемнение у земли — множитель с
  уходом в синеву (`AO_*` в палитре); под зданием лежат декали вытоптанной земли и умножающего пятна
  тени (`village.groundDecals`). Состав набора задан один раз — `ROLES` и `FEATURES`.
  Правила размеров на телефоне: столб r ≥ 0.09, труба ≥ 0.32 и квадратная, дверь ≥ 0.42, свес ≥ 0.3;
  окна только на стенах шире 1.8. Ступень меняет тип силуэта (число масс и ширину).
  Переведена пока хижина; остальные модели живут в старом коде до раскатки, но уже **склеены**:
  `K.collapse` превращает готовую группу мешей в один меш по правилам набора (материал по
  имени → краска палитры, мировая матрица запекается в геометрию, вызов на материал, контактное
  затемнение `GROUND_AO`). Именованные меши (пламя костра), светящиеся (огонь, горн) и уже
  склеенные остаются отдельными. Той же склейкой собраны стена, леса стройки, окружение, дороги
  и декор посёлка. Новая старая модель без склейки — ошибка: вызовов у неё будет по одному на доску.
- **Фигурки** (`render/figures.ts`) — жители и бойцы рисуются инстансами: шесть частей тела
  (ноги, туловище, голова, шапка, палка, щит), цвет на фигурку через `instanceColor`, девять
  вызовов на всех, сколько бы людей ни было. Агент (`villagers.ts`, `soldiers.ts`) мешей не
  держит — он правит позу своей `Figure`, а матрицы раз в кадр пишет `FigurePool` в сцене.
  Цвета одежды — `JOB_TINT`/`TROOP_TINT` в палитре, новых материалов на фигурку не заводить.
- **Земля** (`render/terrain.ts`) — полярная сетка, ровная внутри расчистки (здания, дороги, стена
  и бойцы на y = 0), с рельефом и чашей за ней (`groundHeight` — чистая функция, детерминированная
  по сиду). Пятна травы и вытоптанность внутри стены — множители в цвете вершин, поэтому зимой они
  же дают сине-серые тени на снегу. Всё, что ставится за расчисткой (окружение, жители, снежинки),
  берёт высоту из `groundHeight`.
- **Стенд** (`render/showcase.ts`, `?showcase=building|village`) — ряд здания по ступеням
  (`type=hut&tiers=0,1,2`) или посёлок заданного уровня (`levels=10`, все постройки разом;
  `buildings=hut:10,smithy:3` правит отдельные); силуэтный режим, честный счёт вызовов с теневым
  проходом (`info.autoReset = false`), снимок в файл через `?snap=имя` → `snaps/`. Бюджет: посёлок
  на потолке — ≈150 вызовов и ≈70k треугольников (лес и тени), потолок — 450 вызовов. Частота
  кадров меряется на телефоне: `?perf=8` крутит камеру восемь секунд и шлёт итог на dev-сервер
  (`POST /__perf` → `snaps/perf.jsonl`); открывать стенд с телефона по адресу машины в локальной
  сети (`vite --host`). Меняешь модель или свет — снимай стенд, не описывай словами.
  **Стенд собирается и в продакшен** — это инструмент, а не отладочная ветка: гейта по
  `import.meta.env.DEV` у него нет и заводить его нельзя, иначе на выложенном адресе
  замерить телефон будет негде. В продакшене адресов `/__perf` и `/__snap` не существует:
  тогда итог замера остаётся на экране, а тап по подписи кладёт отчёт целиком в буфер обмена.
  В игру стенд не попадает — он лежит отдельным чанком и грузится только по `?showcase=`.

## У костра стоят свободные руки

Ходьбы на работу и обратно нет и не должно появиться. Она стоила дорого — путь, поворот,
покачивание на каждого работника каждый кадр — и не сообщала ничего: на 390 px не видно, кто куда
пошёл. Хуже, она давала обратный смысл: чем лучше идут дела, тем пустее деревня, потому что все
разошлись по углам.

- **На площади видно ровно свободные руки.** Житель с `job === 'idle'` гуляет у костра, назначенный
  на работу исчезает со сцены, снятый — возвращается (`render/villagers.ts`, `Scene.sync`).
  Сколько человек у огня — столько и можно назначить, и это видно, не открывая ни одной панели.
- Больше `MAX_VILLAGERS` (10) фигурок разом не показывается: в толпе свободные руки не сосчитать,
  а счёт — весь смысл площади. Дружина считается отдельно (`MAX_SOLDIERS`): она не свободные руки.
- **Занятость показывает здание, а не человек** (`render/worksigns.ts`, таблица `WORK_SIGN`).
  Признак загорается, когда в здании есть рабочие, и гаснет, когда их нет: груз у стены (лежит один
  тюк, второй ходит вверх-вниз), дым из трубы, горн у кузницы. Ходьбы и поиска пути нет.
  Склад — единственное исключение из правила «есть рабочие»: их у него не бывает вовсе, поэтому
  мешки он показывает по запасам (`STORAGE_SHOWN`).
- Цена всего этого — два вызова отрисовки: один на все грузы разом (инстансы, цвет через
  `instanceColor`) и один на весь дым труб (точки). Горн был в модели кузницы и раньше — он просто
  гаснет без кузнецов, поэтому его имя `forge` нельзя менять: по нему сцена его и находит.
  Дым очага и дым труб — две системы точек, а не одна: размер и плотность у точек задаются
  материалом, то есть одни на всё облако, а трубе нужна заметнее очага (`FIRE_LOOK`/`CHIMNEY_LOOK`).
- Проверять глазами: `?showcase=village&levels=10` — посёлок укомплектован, у костра
  пусто, у дворов груз и дым; тот же адрес с `&workers=none` — все руки свободны, у костра десяток,
  признаков работы нет ни у одного здания.

## Планировка поселения

Автоподбора свободного места нет. У каждого типа здания своё **именованное место** на круговой
планировке — `render/plan.ts`, чистые числа без three.js, чтобы их можно было проверить тестом.

- Кольца от центра: площадь (костёр и колодец) → Дом вождя, хижина, святилище, укрытие →
  склад, мастерская, кузница, казармы, рынок у ворот → производство (лесопилка, каменоломня,
  навес собирателей, охотничий домик, ферма, загон, рудник) → стена.
- **Радиус стены задан раз и навсегда** (`WALL_RADIUS`), и место под каждое здание зарезервировано по
  габаритам его **третьей визуальной ступени на десятом уровне** (`MODEL_RADIUS` × `PLAN_SCALE` ×
  `levelScale(10)`). Иначе к концу партии крыши вылезут за стену и друг на друга.
- Кольца идут в шахматном порядке: второе смещено на полшага от первого, третье — от второго. Ворота
  приходятся на просвет первого кольца и на пустое место второго, поэтому главная улица ни во что не
  упирается. Углы записаны числами: место здания — факт, который должно быть видно глазом в таблице.
- Каждое здание развёрнуто фасадом к центру (`facingCenter`): перёд модели — её `+z`.
- Ворота всегда в одном месте и смотрят в камеру при стартовом ракурсе (`GATE_ANGLE` выведен из
  азимута камеры). Кадр камеры привязан к радиусу стены, а не к постройкам (`Scene.applyFraming`).
- Дороги (`render/village.ts`) тоже родом из плана: кольцевая вокруг площади, окружная под стеной,
  главная улица от ворот и отводы к каждому зданию. Покрытие одно — мощёный камень.
- Свободные места плана (там, где раньше стояло хранилище знаний, и `SPARE_PLOTS`) заняты
  хозяйством: поленницы, бочки, телеги, сушила, загородки с животными. Декор лежит отдельной
  группой `decor` — по ней тест проверяет, что изнутри он не наезжает на стену.
- **Рынок стоит прямо на воротах** — единственное здание, сквозь которое главная улица идёт
  нарочно (`ROAD_THROUGH`): торговые ряды по обе стороны проезда, между ними дорога, по ней
  выезжает караван. Отвода у него нет — улица от ворот и есть его подъезд. Модель обязана держать
  проезд шириной `THROUGH_HALF` свободным, и это отдельный тест.
- `render/plan.test.ts` держит всё это: габариты совпадают с настоящими моделями, площадки не
  пересекаются, всё внутри стены, площадь свободна, дороги не идут сквозь постройки, фасады смотрят
  в центр. **Меняешь модель — прогоняй этот тест и правь `MODEL_RADIUS`.**

## Зона расчистки вокруг поселения

У посёлка есть **зона расчистки**: `CLEAR_RADIUS = WALL_RADIUS + CLEAR_MARGIN` (`render/plan.ts`).

- Внутри этого круга нет ничего, кроме самого поселения, дорог и стены: ни деревьев, ни камней,
  ни кустов, ни прочего декора.
- Расстановка детерминирована по сиду — позиции считаются хешем. Позиция внутри запретной зоны
  не двигается «куда-нибудь рядом», а **отбрасывается**. Сдвиг ломал бы узнаваемый рисунок угодий
  и всё равно мог упереться в стену. `inCleared(x, z, r)` учитывает габарит объекта: за черту не
  должна выходить и крона.
- Перед воротами по направлению дороги оставлен свободный коридор (`GATE_CLEAR_HALF`): выезд не
  упирается в лес, и по нему идёт караван.
- По краю расчистки стоит полоса вырубки шириной `CLEAR_EDGE`: пни, поваленные стволы, срезанный
  подлесок. Без неё граница читалась бы дырой в лесу, а не расчищенным местом.
- За полосой вырубки — сплошной лес до края мира (`FOREST_FROM`), с прогалинами под угодья
  (`GLADES`): у скал, ягодника и полей деревья расступаются, охотничья зона — редколесье.
  Посёлок должен читаться поляной в лесу, а не кольцом посреди пустого зелёного диска;
  `CLEAR_MARGIN` — 3.2, больше не надо.
- **Лес стоит дёшево, и это условие его существования.** Сплошной пояс не добавляет ни одного
  вызова отрисовки (он склеен), но давал 45 тысяч треугольников из 115 тысяч. Резать его нельзя —
  он и держит композицию, — поэтому вместо резки сняты две платы: окружение **не отбрасывает тень**
  (`collapse(root, GROUND_AO, false)`): коробка теней накрывает только посёлок (`WALL_RADIUS + 2`),
  а склеенный меш культуре не поддаётся и уходил в теневой проход целиком; и дальние деревья
  (за `FOREST_FAR`) рисуются одним конусом без ствола и без донца (`makeFarTree`, `openEnded`) —
  пять треугольников против сорока четырёх. Новый объект окружения обязан вписаться в это: тень
  ему не положена, а модель у края мира — самая грубая, какую терпит силуэт.
- Угодья (`ZONES`) вынесены за эту границу, `WORLD_RADIUS` вырос до 30.
- `render/terrain.test.ts` держит обещание: ни один объект окружения не попадает внутрь радиуса,
  кольцо стены третьей ступени не пересекается ни с окружением, ни с декором посёлка,
  а коридор перед воротами свободен.

## Структура

- `src/game/` — чистая симуляция, без React и three.
  - `types.ts`, `constants.ts` — состояние и константы (день = 60 сек, уровни и множители зданий,
    `BUILDER_RATE`, `CRAFTER_BUILD`, `BASE_DEFENSE`, `MORALE_BASE`).
  - `data/` — контент: `buildings.ts`, `jobs.ts`, `quests.ts`, `events.ts`, `names.ts`, `seasons.ts`,
    `policy.ts` (указы, рацион, налог, `TAX_PER_POP`), `equipment.ts` (снаряжение), `troops.ts`

    проводки первых шагов).
    `seasons.ts` — вся сезонная конфигурация: `SEASON_DAYS` (5 дней = 5 минут на сезон), таблица `SEASON_MODIFIERS`,
    отопление, смягчение первой зимы.
  - `derived.ts` — производные величины (уровни и слоты зданий, вместимость, множители, мораль,

    зимы, маркеры внимания `buildingAttention`, критические тревоги `alerts`).
  - `sim/tick.ts` — шаг симуляции (нормализация назначений, производство, улучшения, ковка, учения,
    рынок, рост, события, задания); `catchUp` — офлайн-догон.

    `normalizeAssignments`, `autoAssign`.
  - `sim/smithy.ts` — ковка снаряжения; `sim/army.ts` — наём, очередь казарм, потери армии;

    офлайн-прогресс до 4 ч.

  - `types.ts` — доменные типы: клетка, поселение, поход, отчёт, разведданные, племя.

## Правила

- Симуляция мутирует состояние на месте; стор после действия делает `set({ s: { ...s } })`, чтобы React перерисовался.
- Новый контент добавляется в `data/*` и, при необходимости, в `derived.ts`,
  `render/buildings.ts` (модель) + `FOOTPRINT` и `render/plan.ts` (место и `MODEL_RADIUS`).
  Новое здание попадает в стартовый посёлок само: `createInitialState` ставит всё из `BUILDINGS`.
- Тексты интерфейса — на русском. Эмодзи используются как иконки в UI.
  Проверяй, что символ рисуется: эмодзи Emoji 13.0 и новее (🪵, 🪨, 🪙) на части систем показываются квадратом.
- Для файлов с эмодзи писать через Write, не через bash-heredoc (обрезается на некоторых символах).
- Размеры и отступы берутся из CSS-переменных `--app-h`, `--safe-*`, `--nav-h`, `--tap` (44 px) — не `100vh` и не голый `env()`.
- Изменение формата сохранения: поднять `SAVE_VERSION` в `state.ts`. Миграций нет с версии 5 —
  сохранение младшей версии отбрасывается с объяснением игроку (`LegacyModal`). Новые поля
  состояния со значением по умолчанию версию не поднимают: `deserialize` мержит сохранение поверх
  `createInitialState()` (словари счётчиков — `equipment`, `army`, `stats` — мержатся отдельно,
  иначе новый вид бойца приедет как `undefined`). Если понадобится снова приводить старые сохранения,
  писать цепочку миграций заново и обязательно с записью в летопись: прогресс не пропадает молча.
- Сезон меняет баланс только через таблицу `SEASON_MODIFIERS`. Логика читает её в одном месте — `seasonMods(s)` в
  `derived.ts`, а `tick` берёт множители один раз за шаг и передаёт вниз. Новый сезонный эффект добавляется полем
  в `SeasonModifiers`, не условием по коду.
- Сезон и год выводятся из `s.time`, отдельного состояния нет: `seasonOf`, `yearOf`, `seasonProgress`.
  Первая зима (год 1) мягче — её штрафы гасятся `FIRST_WINTER_SOFTEN`.
- Модалки делят один слой: новая не должна накладываться на `EventModal` — смотри guard в `WinterModal`.
- Склад стоит в посёлке с первого дня: полный список ресурсов виден только в его панели, без него
  игрок не видит ни одного числа о запасах.
- Здания одного типа второго не бывает, и снести здание нельзя: событие отнимает уровень, а не
  постройку. Пожар отнимает уровень хижины, но не ниже первого (`data/events.ts`).

## Здания: все стоят, растут уровнями

Каждого типа в посёлке ровно одно здание, все они стоят с первого дня, и вся линия развития
постройки — уровни. Отсюда следует всё остальное:

- Улучшение — стройка на уже стоящем здании: `workRequired > 0` (`isSite`). Оно ничего не
  отключает: `buildingSlots` и `placeMultiplier` смотрят на `level`, а он при улучшении не меняется —
  рабочие остаются на местах, выработка идёт, новый слот добавляется к старым в момент завершения.
  Всё строится одной очередью — `currentSite(s)`; работают свободные жители (`BUILDER_RATE`) и
  ремесленники мастерской (`crafterBuildRate`).
- Слотов столько же, сколько уровней (`buildingSlots`), каждый уровень даёт +10% выработки каждому рабочему
  (`levelOutputMult`). Цена и труд улучшения растут в `UPGRADE_GROWTH` (1.4) раза за уровень от
  `def.cost`/`def.work`.
- Потолок уровня — минимум из `def.maxLevel` и `MAX_BUILDING_LEVEL` (10). Ничем сверху не режется.
- Пассивные эффекты (жильё, склад, защита, мораль) растут не множителем, а полем `perLevel` в определении
  здания; поле `since` задаёт уровень, с которого эффект вообще появляется (жильё Дома вождя — с шестого).
  Числа подобраны так, чтобы на потолке население доходило до 40+ человек.
  Меняя `perLevel`, прогоняй тест «на потолке уровней мест работы примерно столько же, сколько людей».
- Кто где работает, хранится только в жителе: `job` + `workplace`. Список рабочих здания собирается перебором
  (`workersIn`), дублирующего массива нет. `normalizeAssignments` вызывается каждый тик и чинит назначения после
  любых изменений мира; житель без места остаётся при профессии, только если она разрешает вольный сбор.

## Карта мира

Мультиплеера и сервера нет: мир генерируется и живёт на клиенте. Но код написан так, чтобы источник
данных менялся без переписывания экранов.

- **Вся работа с миром идёт через `worldApi()`** — список поселений в области, карточка, отправка похода,
  свои походы, отчёты, разведданные, племена. Ни один компонент не лезет в `LocalWorld` напрямую и не
  импортирует его (кроме `world/store.ts`, который его подключает). Появится сервер — рядом встанет
  `HttpWorld` с тем же интерфейсом.
- **Все методы асинхронные, даже локальные.** Синхронный вызов «потому что данные рядом» — ошибка:
  при переезде на сервер придётся править каждое место вызова.
- **Мир детерминирован по сиду.** Ландшафт клетки — чистая функция `terrainAt(seed, x, y)`, поселения —
  `generateWorld(seed)`, бой — `resolveBattle({ seed: марш.seed, ... })`. Сервер должен уметь повторить
  расчёт и получить то же самое, поэтому в этих местах нельзя звать `Math.random()`.
- **Время пути симметрично.** `terrainFactor` приводит концы отрезка к одному порядку и берёт пробы в
  серединах равных долей — путь туда и обратно считается по тем же клеткам. Обратная дорога получается
  из той же длительности (`turnHome`), отзыв — из уже пройденного времени.
- **Разведка стареет.** Снимок хранит время; `readIntel` отдаёт точное число, потом диапазон, потом ничего
  (пороги — `INTEL_*` в `data/tuning.ts`). Своя мощь видна всегда, чужая — только из разведки или боя.
- **Армия в походе не защищает деревню.** Ушедшие живут числами `warriorsAway`/`scoutsAway` в состоянии
  племени, их вычитают `defense()` и `buildRate()`. Число не хранится дважды: `syncAway` каждый пульс
  выводит его из списка походов, поэтому потерянное сохранение мира не оставит деревню без армии.
  Панель отправки обязана показывать, какой станет оборона. Мир считает отряд числами, поэтому в него
  уходит средняя мощь бойца (`soldierPower`), а состав знает только племя.
- **ИИ ходит мягко.** Набег редкий, слабее обороны игрока (`AI_POWER_VS_DEFENSE`) и виден заранее
  (`AI_WARNING`) — в `AlertBar` с таймером. Набег, пришедшийся на время без игрока, не состоится.
- **Замки — крепкие цели с казной, видны с первого дня.** Флаг `castle` стоит в генерации и
  детерминирован по сиду. Замок заметно крепче обычного поселения (`CASTLE_POWER`), а взятое золото
  соразмерно тому, сколько гарнизона удалось выбить, — слабый отряд не вынесет ничего и оставит
  там половину своих. Ближе `CASTLE_MIN_DISTANCE` от дома замков не бывает: первая цель на карте
  не должна быть крепостью. Золото едет домой той же добычей, отдельным ключом `Loot.gold`;
  привезённое золото засчитывает племени взятый замок (`stats.castles`).
- **Карта и сцена не рисуются одновременно.** `mapOpen` в сторе гасит рендер-луп `TribeScene.pause()`,
  но сцена не разрушается: `sync` продолжает идти, возврат не перезагружает геометрию. Проверено:
  шесть переходов туда-обратно не меняют ни число canvas, ни `renderer.info.memory`.
- **Числа мира правятся в `data/tuning.ts`**, а не по коду.
- Мир сохраняется своим ключом `tribe.world.v1` в localStorage, без CloudStorage: это временное
  состояние клиента, на сервере его не будет. Версия формата — `WORLD_SAVE_VERSION` (2); чужая
  версия читается как «мира нет», и он генерируется заново. «Начать заново» в заданиях пересоздаёт
  и мир (`resetWorld`).
- Чего в этом этапе нет и что не надо доделывать по дороге: торговля между игроками, порты, мосты,
  перевалы, зоны влияния, временные события на карте, фильтры сверх базовых. Место в данных
  заложено (`lootMix`, `Rect`, стадии, вторая вкладка рынка), реализации быть не должно.

## Бой

Боевая система описана в [docs/BATTLE_SYSTEM_FOR_CLAUDE.md](docs/BATTLE_SYSTEM_FOR_CLAUDE.md) —
**читать целиком перед любой работой над боем**. Сделано пока только ядро: `src/battle/`.
Интерфейса подготовки, 3D-показа, отчёта на экране, шаблонов, сервера, разведки и заморозки
обороны нет — они идут следующими шагами и не должны появляться по дороге.

- **`simulateBattle(input)` — чистая детерминированная функция.** На вход состав и настройки
  обеих сторон плюс сид, на выход исход, потери и журнал. Модуль ни от чего не зависит: ни
  `@/`-импортов, ни React, ни three, ни состояния игры, ни `Math.random`. Это условие того, что
  ровно этот код потом запустит сервер, а клиент прогонит его же для показа. Новый импорт извне
  в `src/battle/` — ошибка.
- **Все числа — в `battle/config.ts`.** Треугольник контрров (`COUNTER`), характеристики родов
  (в том числе базовая мораль), снаряжение (`GEAR`), характер (`TEMPER`), тики фаз, мораль
  (`MORALE`), планы, приказы. Логика в `sim.ts` только читает таблицы; баланс правится без
  правки логики. Числа кольца (×2.0, ×1.8, ×0.5, ×1.5, ×0.8, ×0.7) стоят как в документе;
  конница против пехоты — ×1.3 (документ поправлен: при ×1.0 одна пехота была почти оптимальна).
- **Мораль своя у каждого сектора**, не у армии. Сектор с нулевой моралью бежит и не держит
  линию, паника перекидывается на соседей, армия отступает, когда сломанные сектора весят
  половину или линии больше нет. Это и есть нормальный конец боя: до гонга доживают доли
  процента. Ограничитель держит тест: при перевесе 10% размен не выше ≈1.5 — сломанная армия
  выходит из контакта сразу, потолок преследования 4%, фаза морали после слома обрывается.
  Мораль — характеристика рода (пехота ниже копейщиков) плюс ступени снаряжения `gear`
  в расстановке; характер родов — множитель потерь морали по ситуации. В модели морали каждая
  лишняя потеря стоит дорого: планы выровнены заново (матрица «план против плана» в отчёте),
  копьям снижена база — при 70 они не проигрывали никому.
- **Шесть секторов и резерв, девять фиксированных фаз.** Полоса 0 — левый фланг со стороны
  своей армии; левый фланг нападающего стоит против правого фланга обороняющегося (`facing`).
  Бой всегда укладывается в 50–100 тиков: стрелковая фаза 8–20 (темп планов), остальные
  фиксированы, бой линий может оборваться раньше, когда сторона сломалась, — тогда обходы и
  ввод резерва пропускаются, а фаза морали, отступление и преследование идут всегда.
- **Превосходство условно.** Копья ×2.0 против конницы только пока держат линию (`advance` даёт
  ×1.2); конница ×0.5 о сомкнутые копья — в лоб или в закрытый тыл (тыловое каре сомкнуто со всех
  сторон, фронт — только спереди); лучники после того, как их цель вошла в рукопашную, бьют
  ×0.3 (`afterContact`), а «держать дистанцию» работает только против тех, кто медленнее. Копья
  медленные: пока быстрых нет ни у кого, рукопашная начинается на `SLOW_CONTACT.delay` позже.
- **Журнал — часть ядра, не украшение.** События именованные (`BattleEvent`), с фазой, тиком,
  стороной и сектором: залп до контакта, копья остановили удар, конница вырубила лучников, фланг
  обойдён, сектор смят, резерв вошёл, мораль рухнула, проиграли размен. События о размене
  выводятся из матрицы «кто кого выбил» по полосам (`kills`), порог значимости — `EVENT_MIN`/
  `EVENT_SHARE`. Отчёт потом строится из журнала; событие, которого нет в журнале, в отчёт
  не попадёт, поэтому новая механика обязана писать своё событие.
- **Быстрая атака — четыре пресета** (`QUICK_PRESETS`: стандарт, анти-кавалерия, удар по
  центру, оборона), `quickAttack(army, seed, intel)` берёт один по сиду похода детерминированно,
  свежие разведданные сдвигают веса. `quickSetup` — стандартный пресет, им пользуются тесты.
  Известный контрер стандарта выигрывает у него ≈75%, у случайного пресета — ≈20%: контрить
  нечего, пока не знаешь, какой пришёл. Настроенная армия (`bench.ts`, `TUNED`) против быстрой
  атаки — ≈17%, коридор 10–25% держит тест; потолок по перебору 192 расстановок ≈25%.
  Пресет без якоря пехоты на флангах — ловушка (проигрывал заякоренным на 40–90%), резерв
  с приказом «держать фланг» выходит навстречу обходу — иначе тыл любого пресета открыт.
- **Тесты — раздел 16 документа целиком** (`battle.test.ts`): нет доминирующего состава,
  разрыв быстрой атаки и известный контрер, кольцо по парам, условность превосходства,
  досрочный конец боя, ограничитель перевеса 10%, паника и якорь, мораль как характеристика
  и снаряжение, пресеты, детерминированность, 50–100 тиков, осмысленный и непротиворечивый
  журнал. Наборы для них — в `bench.ts`, и те же наборы печатает `npm run battle:report`
  (матрица составов с победами/ничьими/поражениями и разменом, кольцо, планы, пресеты, разрыв,
  длительность с долей досрочных, ограничитель; `SHOW=а:б SEED=n SCALE=1.1` — журнал одного
  боя с моралью секторов и потерями по фазам). `npm run battle:sweep` с `GRID='[{...}]'` —
  быстрый перебор чисел конфига. **Меняешь число в конфиге — смотри отчёт, не гадай.**
  Баланс в модели морали стоит на лезвии: в зеркале одинаковых армий перевес в 5% даёт 10/0/0,
  поэтому **все пороги — по размену** (`RATIO_EVEN`), а не по счёту побед; счёт поля в отчёте
  показывается рядом, но выводов по нему нет. Поле держит тот, у кого дольше мораль (копья), и
  это замысел — не чинить; следствие закрыто третьей категорией исхода: **победа с непомерными
  потерями** (`pyrrhic`, размен ниже `PYRRHIC_BELOW`), у каждой стороны `verdict`, журнал
  называет её прямо. Составы без пешей линии в ограничителе держат свой потолок
  (`OVERSIZE_CAP.noLine`), а не исключены из него.
