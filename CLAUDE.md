# TRIBE — Telegram Mini App

Лёгкая low-poly 3D-стратегия о развитии племени: от пяти человек у костра до раннего государства.
Полное видение — в [docs/concept.md](docs/concept.md). Заход 3–5 минут: тапнуть по зданию, поставить туда людей,
начать стройку или улучшение, принять решение в событии.

## Стек

- Vite + TypeScript + React 18 (2D-интерфейс поверх сцены)
- three.js (low-poly диорама, OrbitControls с ограничениями под тач)
- zustand (единый стор), vitest (тесты симуляции)
- Telegram WebApp API через `window.Telegram.WebApp` (скрипт в index.html); сохранение в localStorage + CloudStorage

## Команды

```bash
npm run dev        # dev-сервер (vite --host)
npm run build      # tsc + vite build → dist/
npm test           # vitest
npm run typecheck
```

## Диегетический интерфейс

Данные живут не в глобальных панелях, а внутри зданий. Одно правило без исключений:

- у каждого здания своя панель, она открывается тапом по зданию в сцене или из списка в «Зданиях»;
- панель у всех одинаковая: шапка (иконка, название, уровень, кнопка улучшения), слоты рабочих,
  собственные данные здания, его действия — см. `ui/panels/BuildingPanel.tsx`;
- ресурсы и снаряжение целиком видны только на складе, дерево технологий — только в хранилище знаний,
  вольный сбор и мораль — у костра, эпоха, указы и рацион — в Доме вождя, ковка — в кузнице,
  наём — в казармах;
- нижняя навигация — только то, что не привязано к месту: «Племя», «Здания», «Задания».
  «Здания» (`ui/panels/BuildPanel.tsx`) — это и список посёлка, и стройка: сначала «В работе»,
  потом «Построено» (тап открывает панель здания), потом «Можно построить» (тап начинает стройку).
  Отдельной кнопки «Посёлок» нет — она дублировала бы этот же список. Тап по крыше в сцене
  остаётся, но основной путь к зданию — список: на 390 px пальцем по крыше не попасть.

Игрока нельзя запереть за зданием: исследования идут у костра вполсилы, пока нет хранилища знаний,
а добыча без профильного здания работает «вольным сбором» (`FREE_RANGE_MULT`).

## Две шкалы: стадия и эпоха

Видимая шкала одна — **стадия поселения**: Лагерь → Племенное поселение → Деревня → Укреплённая
деревня → Город (`data/stages.ts`, `settlementStage`). Она стоит в строке состояния и считается по
тому, что видно в кадре: население (жители + бойцы + новобранцы), число достроенных зданий, сумма их
уровней и уровень стены. Город без стены не бывает — это отдельное требование стадии.

**Эпоха** (`ERA_TECHS` в `data/techs.ts`, `era`) — технический уровень. Двигается только технологиями,
задаёт потолок уровней зданий (`ERA_MAX_LEVEL`) и материалы построек (`ERA_STYLE`). В HUD её нет:
её показывают в Доме вождя вместе со списком того, чего не хватает до следующей.

Ни население, ни число построек на эпоху не влияют, и наоборот — знания не двигают стадию. Смешивать
их обратно нельзя: игрок должен видеть одну шкалу и понимать, чем она растёт.

## Дом вождя: указы и рацион

`data/policy.ts` — единственное место, где записано, что делают указ и рацион. Логика только читает
таблицу: `decreeOf`/`rationOf`, множитель выработки в `jobMultiplier`, множитель расхода в
`foodConsumptionPerDay`, дневной сдвиг морали в `tick` через `policyMoralePerDay`.

- Последствия пишутся словами в поле `effect` — этот текст стоит **на кнопке**, а не в подсказке.
- Числа должны сходиться ровно: тест сверяет выработку и расход с объявленной величиной.
- Слово «налоги» не используется: монеты в игре нет.
- Дом вождя с 6 уровня даёт жильё — через поле `since` в определении здания. Без этого стадия
  «Город» недостижима по населению.

## Снаряжение и войско

- **Снаряжение** (`data/equipment.ts`) — счётчики в `s.equipment`, а не ресурсы. Вместимость склада
  на них не действует (полный склад молча остановил бы кузницу) и чужой набег их не уносит.
  Видны они всё равно на складе, отдельным разделом.
- **Кузница** кует выбранное (`s.forging`), скорость — из числа кузнецов, уровня здания и таланта
  (`forgeRate` через `villagerMultiplier`). Не хватает материалов — заготовка ждёт, а панель пишет,
  чего именно. Молчаливого тупика быть не должно.
- **Войско** (`data/troops.ts`) — счётчики в `s.army`. Боец не житель с профессией: роли «воин» в
  `JobId` нет. Цена найма — ресурсы + снаряжение + один свободный житель + время учений; всё
  списывается сразу, как за стройку. Ушедшие на учения хранятся в самом заказе (`RecruitOrder.people`),
  поэтому отмена возвращает тех же людей, а не безымянные головы.
- Очередь найма одна и идёт последовательно; остаток работы переходит следующему заказу.
- **Мощь армии считается из состава отряда** (`armyPower`) и ничем больше не множится: снаряжение уже
  вложено в вид бойца. Эту же мощь берёт карта мира через `soldierPower` в `world/bridge.ts`.
- Бойцы едят (`SOLDIER_FOOD`), но жилья не требуют: они живут в казармах.

## Проводка первых шагов

Новичок видит костёр в чистом поле, и ему негде прочитать правила: полосы ресурсов нет, данные спрятаны
в здания. Поэтому первая партия ведётся за руку — `game/data/tutorial.ts` (шаги) и `ui/TutorialOverlay.tsx`
(строка и «дырка» в затемнении).

- Ни одного шага без действия игрока: экранов с «Далее» нет, шаг закрывается настоящим тапом
  в настоящем интерфейсе. Исключение — две строки-заставки, они закрываются тапом в любом месте.
- Шаг засчитывается по факту (`done(s, ui)`), а не по порядку: построил лесопилку до просьбы — шаги про
  неё проматываются. Условие пишется щедро, чтобы игрок не застрял на уже сделанном.
- Симуляция не останавливается. Слой ничего не перехватывает: затемнение — это тень самой «дырки»
  (`box-shadow` наружу), у неё `pointer-events: none`.
- Подсветка здания считается проекцией из 3D (`TribeScene.screenSpot`) каждый кадр — она не отстаёт
  при повороте камеры. Подсветка интерфейса ищется по `data-tut`.
- Прогресс живёт в сохранении (`tutorialStep`, `tutorialDone`), а не в отдельном ключе localStorage.
  Старым сохранениям обучение выключается в `deserialize`.
- Пока обучение идёт, `tick` придерживает случайные события — но не дольше `TUTORIAL_EVENT_MUTE`,
  иначе брошенное на середине обучение выключило бы их навсегда.
- Отладка: «Задания» → «Служебное» → «Пройти обучение заново».

## Визуальный рост зданий

Уровень виден в сцене, иначе он остаётся числом в панели.

- Три ступени на здание: уровни 1–3, 4–7, 8–10 (`VISUAL_TIERS`, `visualTier`). Каждая следующая заметно
  крупнее и подробнее: у хижины появляется пристройка, потом крыльцо и труба; у рудника — копёр, потом
  колесо и рельсы; у Дома вождя — палата, потом донжон с зубцами.
- Внутри ступени постройка ещё подрастает масштабом (`levelScale`), а весь посёлок ужат общим
  множителем плана `PLAN_SCALE`: модели рисовались под прежнюю вольную расстановку и для кольцевого
  посёлка велики. Стена — исключение: она и есть это кольцо, её масштабировать нельзя.
- Материалы берутся из `ERA_STYLE[era]` — одна таблица на все здания: шкуры и жерди → солома → тёс →
  камень с дранкой → штукатурка с черепицей. Новый материал крыши надо добавить и в `render/season.ts`,
  иначе зимой он не побелеет. То же для новых материалов дорог и разметки.
- Модель пересобирается только при смене ступени, эпохи или этапа стройки — не на каждом уровне.
- Стройка нового здания идёт этапами (площадка → каркас → здание), а улучшение модель не трогает:
  вокруг неё появляются леса (`scaffold`), здание работает, рабочие ходят туда же.

## Планировка поселения

Автоподбора свободного места больше нет. У каждого типа здания своё **именованное место** на круговой
планировке — `render/plan.ts`, чистые числа без three.js, чтобы их можно было проверить тестом.

- Кольца от центра: площадь (костёр и колодец) → Дом вождя, хижина, хранилище знаний, святилище →
  склад, мастерская, кузница, казармы (место у ворот оставлено под рынок) → производство (лесопилка,
  каменоломня, навес собирателей, охотничий домик, ферма, загон, рудник) → стена.
- **Радиус стены задан раз и навсегда** (`WALL_RADIUS`), и место под каждое здание зарезервировано по
  габаритам его **третьей визуальной ступени на десятом уровне** (`MODEL_RADIUS` × `PLAN_SCALE` ×
  `levelScale(10)`). Иначе к концу партии крыши вылезут за стену и друг на друга.
- Кольца идут в шахматном порядке: второе смещено на полшага от первого, третье — от второго. Ворота
  приходятся на просвет первого кольца и на пустое место второго, поэтому главная улица ни во что не
  упирается. Углы записаны числами: место здания — факт, который должно быть видно глазом в таблице.
- Каждое здание развёрнуто фасадом к центру (`facingCenter`): перёд модели — её `+z`.
- Ворота всегда в одном месте и смотрят в камеру при стартовом ракурсе (`GATE_ANGLE` выведен из
  азимута камеры). Кадр камеры привязан к радиусу стены, а не к постройкам, — поэтому он не дёргается
  при каждой новой крыше (`Scene.applyFraming`).
- Дороги (`render/village.ts`) тоже родом из плана: кольцевая вокруг площади, окружная под стеной,
  главная улица от ворот и отводы к каждому построенному зданию. Со стадией меняется только покрытие:
  тропинка → утоптанная земля → мощёный камень.
- Пустые места видны размеченными площадками и по мере роста обрастают декором: поленницы, бочки,
  телеги, сушила, загородки с животными.
- `render/plan.test.ts` держит всё это: габариты совпадают с настоящими моделями, площадки не
  пересекаются, всё внутри стены, площадь свободна, дороги не идут сквозь постройки, фасады смотрят
  в центр. **Меняешь модель — прогоняй этот тест и правь `MODEL_RADIUS`.**

## Структура

- `src/game/` — чистая симуляция, без React и three.
  - `types.ts`, `constants.ts` — состояние и константы (день = 60 сек, уровни и множители зданий).
  - `data/` — контент: `buildings.ts`, `techs.ts`, `jobs.ts`, `quests.ts`, `events.ts`, `names.ts`, `seasons.ts`,
    `stages.ts` (стадии поселения), `policy.ts` (указы и рацион), `equipment.ts` (снаряжение),
    `troops.ts` (войска), `tutorial.ts` (шаги проводки первых шагов).
    `seasons.ts` — вся сезонная конфигурация: `SEASON_DAYS` (5 дней = 5 минут на сезон), таблица `SEASON_MODIFIERS`,
    отопление, смягчение первой зимы.
  - `derived.ts` — производные величины (уровни и слоты зданий, вместимость, множители, эпоха и стадия,
    мораль, армия и оборона, кузница, сезон и прогноз зимы, маркеры внимания `buildingAttention`,
    критические тревоги `alerts`).
  - `sim/tick.ts` — шаг симуляции (нормализация назначений, производство, стройка, ковка, учения,
    исследование, рост, события, задания); `catchUp` — офлайн-догон.
  - `sim/workers.ts` — кто где работает: `assignWorker`, `unassignWorker`, `changeFreeJob`,
    `normalizeAssignments`, `autoAssign`.
  - `sim/smithy.ts` — ковка снаряжения; `sim/army.ts` — наём, очередь казарм, потери армии.
  - `sim/actions.ts` — действия игрока; возвращают `null` или текст ошибки.
  - `store.ts` — zustand-стор, игровой цикл (тик 500 мс), автосохранение, состояние шторки (`SheetView`).
  - `save.ts` — сериализация, миграция сохранений, слияние localStorage/CloudStorage, офлайн-прогресс до 4 ч.
- `src/render/` — three.js: `Scene.ts` (свет, день/ночь, выбор здания тапом, маркеры, синхронизация с состоянием),
  `plan.ts` (фиксированный план посёлка: кольца, места, площадки, дороги — без three.js),
  `village.ts` (площадь, колодец, дороги, размеченные площадки, декор), `terrain.ts` (ландшафт и угодья
  за стеной), `buildings.ts` (модели, ступени, материалы эпох, этапы стройки, леса при улучшении, стена),
  `villagers.ts` (агенты жителей), `soldiers.ts` (агенты бойцов: ворота, дозор, учения),
  `season.ts` (палитра сезона, перелив за ~2.5 с), `weather.ts` (снег и дым).
- `src/ui/` — React: `TopBar` (строка состояния со стадией), `AlertBar` (критические состояния),
  `TutorialOverlay` (проводка первых шагов),
  `BottomNav`, `Sheet` (нижняя шторка 62/85%), `panels/*` (`BuildingPanel`, `BuildPanel` — раздел «Здания»,
  `PeoplePanel`, `QuestsPanel`, `SeasonPanel`), `parts/*` (`Cost`, `TechTree`, `ChiefHouse`, `Smithy`,
  `Barracks`, `upgrade` — текст «что даст следующий уровень»), модалки, `GameCanvas`.
- `src/world/` — общая карта мира. Не знает ни про React, ни про three, ни про жителей.
  - `api.ts` — интерфейс `WorldApi` и реестр (`setWorldApi`/`worldApi`) — единственная дверь в мир.
  - `types.ts` — доменные типы: клетка, поселение, поход, отчёт, разведданные, племя.
  - `geo.ts` — координаты, ландшафт клетки по сиду, расстояние, время пути; `gen.ts` — генерация мира;
    `intel.ts` — старение разведданных; `combat.ts` — детерминированный бой по сиду.
  - `data/` — настройки мира: `tuning.ts` (все числа), `units.ts`, `terrain.ts`, `meta.ts` (стадии, отношения, миссии).
  - `local/LocalWorld.ts` — нынешняя реализация `WorldApi`: генерация плюс своя симуляция соседей;
    `local/state.ts` — то, что нельзя вывести из сида (походы, отчёты, разведка, обиды), и его сохранение.
  - `bridge.ts` — единственное место, где мир и племя знают друг о друге: слепок деревни туда,
    последствия походов обратно. `store.ts` — стор экрана карты; `cache.ts` — кэш кусков карты.
- `src/ui/map/` — карта: `WorldMap.tsx` (полотно, жесты, шапка и нижний ряд), `tiles.ts` (растр куска).
  Карточка клетки и походы — обычные панели шторки: `panels/WorldPanel`, `panels/MarchesPanel`.
- `src/telegram/webapp.ts` — обёртка Telegram API: вьюпорт (`--app-h`), вырезы (`--tg-*`), тема из `themeParams`,
  haptics, CloudStorage с чанками.

## Правила

- Симуляция мутирует состояние на месте; стор после действия делает `set({ s: { ...s } })`, чтобы React перерисовался.
- Новый контент добавляется в `data/*` и, при необходимости, в `derived.ts` (эффекты технологий),
  `render/buildings.ts` (модель) + `FOOTPRINT` и `render/plan.ts` (место и `MODEL_RADIUS`).
- Тексты интерфейса — на русском. Эмодзи используются как иконки в UI.
  Проверяй, что символ рисуется: эмодзи Emoji 13.0 и новее (🪵, 🪨, 🪙) на части систем показываются квадратом.
- Для файлов с эмодзи писать через Write, не через bash-heredoc (обрезается на некоторых символах).
- Размеры и отступы берутся из CSS-переменных `--app-h`, `--safe-*`, `--nav-h`, `--tap` (44 px) — не `100vh` и не голый `env()`.
- Изменение формата сохранения: поднять `SAVE_VERSION` в `state.ts` и дописать миграцию в `save.ts` (`migrate`).
  Миграции идут цепочкой (1 → 2 → 3 → 4), каждая — отдельная функция. Версия 3 свела дубли зданий в одну
  постройку с суммой уровней; версия 4 увела воинов из жителей в дружину. Обе написали об этом в летопись:
  прогресс не должен пропадать молча. Новые поля состояния со значением по умолчанию версию не поднимают:
  `deserialize` мержит сохранение поверх `createInitialState()` (словари счётчиков — `equipment`, `army` —
  мержатся отдельно, иначе новый вид бойца приедет как `undefined`).
- Сезон меняет баланс только через таблицу `SEASON_MODIFIERS`. Логика читает её в одном месте — `seasonMods(s)` в
  `derived.ts`, а `tick` берёт множители один раз за шаг и передаёт вниз. Новый сезонный эффект добавляется полем
  в `SeasonModifiers`, не условием по коду.
- Сезон и год выводятся из `s.time`, отдельного состояния нет: `seasonOf`, `yearOf`, `seasonProgress`.
  Первая зима (год 1) мягче — её штрафы гасятся `FIRST_WINTER_SOFTEN`.
- Модалки делят один слой: новая не должна накладываться на `EventModal` — смотри guard в `WinterModal`.
- Склад стоит в посёлке с первого дня: полный список ресурсов виден только в его панели, без него
  игрок не видит ни одного числа о запасах.
- Здания одного типа второго не бывает: `def.max` больше нет, а событие или миграция не должны сносить
  постройку целиком — у неё теперь весь прогресс типа. Пожар отнимает уровень, а не хижину (`data/events.ts`).

## Здания: один тип — одна постройка

Каждый тип строится ровно один раз (`startBuilding` отказывает, если `countAll(s, type) > 0`), и вся
линия развития постройки — уровни. Отсюда следует всё остальное:

- Здание строится 1 уровня: `level: 0` — стройплощадка, `work/workRequired` — текущая стройка.
  Улучшение — такая же стройка на уже стоящем здании: `level > 0 && workRequired > 0` (`isSite`).
  Улучшение ничего не отключает: `buildingSlots` и `placeMultiplier` смотрят на `level`, а он при
  улучшении не меняется — рабочие остаются на местах, выработка идёт, новый слот добавляется к старым
  в момент завершения. Всё строится одной очередью — `currentSite(s)`.
- Слотов столько же, сколько уровней (`buildingSlots`), каждый уровень даёт +10% выработки каждому рабочему
  (`levelOutputMult`). Цена и труд улучшения растут в `UPGRADE_GROWTH` (1.4) раза за уровень.
- Потолок уровня — минимум из `def.maxLevel`, `MAX_BUILDING_LEVEL` (10) и `ERA_MAX_LEVEL[era(s)]`:
  развитие построек привязано к техническому уровню, одну лесопилку в лагере до максимума не закачать.
- Пассивные эффекты (жильё, склад, защита, мораль) растут не множителем, а полем `perLevel` в определении
  здания; поле `since` задаёт уровень, с которого эффект вообще появляется (жильё Дома вождя — с шестого).
  Числа подобраны так, чтобы к раннему государству население доходило до 40+ человек.
  Меняя `perLevel` или `ERA_MAX_LEVEL`, прогоняй тесты «разумная партия доходит до последней эпохи» и
  «разумная партия доходит до стадии „Город“»: они играют автопилотом и проверяют, что верх достижим.
- Кто где работает, хранится только в жителе: `job` + `workplace`. Список рабочих здания собирается перебором
  (`workersIn`), дублирующего массива нет. `normalizeAssignments` вызывается каждый тик и чинит назначения после
  любых изменений мира; житель без места остаётся при профессии, только если она разрешает вольный сбор.

## Карта мира

Мультиплеера и сервера нет: мир генерируется и живёт на клиенте. Но код написан так, чтобы источник
данных менялся без переписывания экранов.

- **Вся работа с миром идёт через `worldApi()`** — список поселений в области, карточка, отправка похода,
  свои походы, отчёты, разведданные, племена. Ни один компонент не лезет в `LocalWorld` напрямую и не
  импортирует его (кроме `world/store.ts`, который его подключает). Появится сервер — рядом встанет
  `HttpWorld` с тем же интерфейсом.
- **Все методы асинхронные, даже локальные.** Синхронный вызов «потому что данные рядом» — ошибка:
  при переезде на сервер придётся править каждое место вызова.
- **Мир детерминирован по сиду.** Ландшафт клетки — чистая функция `terrainAt(seed, x, y)`, поселения —
  `generateWorld(seed)`, бой — `resolveBattle({ seed: марш.seed, ... })`. Сервер должен уметь повторить
  расчёт и получить то же самое, поэтому в этих местах нельзя звать `Math.random()`.
- **Время пути симметрично.** `terrainFactor` приводит концы отрезка к одному порядку и берёт пробы в
  серединах равных долей — путь туда и обратно считается по тем же клеткам. Обратная дорога получается
  из той же длительности (`turnHome`), отзыв — из уже пройденного времени.
- **Разведка стареет.** Снимок хранит время; `readIntel` отдаёт точное число, потом диапазон, потом ничего
  (пороги — `INTEL_*` в `data/tuning.ts`). Своя мощь видна всегда, чужая — только из разведки или боя.
- **Армия в походе не защищает деревню.** Ушедшие живут числами `warriorsAway`/`scoutsAway` в состоянии
  племени, их вычитают `defense()` и `buildRate()`. Число не хранится дважды: `syncAway` каждый пульс
  выводит его из списка походов, поэтому потерянное сохранение мира не оставит деревню без армии.
  Панель отправки обязана показывать, какой станет оборона. Мир считает отряд числами, поэтому в него
  уходит средняя мощь бойца (`soldierPower`), а состав знает только племя.
- **ИИ ходит мягко.** Набег редкий, слабее обороны игрока (`AI_POWER_VS_DEFENSE`) и виден заранее
  (`AI_WARNING`) — в `AlertBar` с таймером. Набег, пришедшийся на время без игрока, не состоится.
- **Карта и сцена не рисуются одновременно.** `mapOpen` в сторе гасит рендер-луп `TribeScene.pause()`,
  но сцена не разрушается: `sync` продолжает идти, возврат не перезагружает геометрию. Проверено:
  шесть переходов туда-обратно не меняют ни число canvas, ни `renderer.info.memory`.
- **Числа мира правятся в `data/tuning.ts`**, а не по коду.
- Мир сохраняется своим ключом `tribe.world.v1` в localStorage, без CloudStorage: это временное
  состояние клиента, на сервере его не будет. «Начать заново» в заданиях пересоздаёт и мир (`resetWorld`).
- Чего в этом этапе нет и что не надо доделывать по дороге: торговля, порты, мосты, перевалы, зоны влияния,
  временные события на карте, фильтры сверх базовых. Место в данных заложено (`lootMix`, `Rect`, стадии),
  реализации быть не должно.
